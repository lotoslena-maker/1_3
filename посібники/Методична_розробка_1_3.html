Після заняття кожний слухач має власну локальну копію репозиторію, виконує простий Python-скрипт і SQL-запит та підтверджує надсилання файлів у GitHub. Викладач оцінює виконані дії та пояснення слухача за визначеними нижче контрольними точками.

2 Мета та очікувані результати

Навчальна мета — сформувати початкові практичні вміння організовувати робочі файли засобів ІАЗ, використовувати Git і GitHub та працювати у VS Code з Python і PostgreSQL.

Розвивальна мета — навчити послідовно перевіряти результат: визначати поточну папку, читати повідомлення інструментів, відрізняти проблему встановлення від проблеми підключення або виконання коду.

Виховна мета — формувати відповідальність за авторство змін, відтворюваність роботи, збереження власних облікових даних та коректну взаємодію у спільному проєкті.

Після заняття слухач уміє:

- пояснити різницю між Git і GitHub, збереженням файла, commit та push;

- створити репозиторій GitHub, клонувати його і знайти власну робочу папку;

- підготувати зміни, створити коміт і перевірити його на GitHub;

- відкрити папку у VS Code, створити файли та обрати інтерпретатор Python;

- виконати check.py і зіставити вивід із контрольним результатом;

- підключитися до локального PostgreSQL, виконати schema.sql та перевірити наявність таблиці;

- записати фактичні результати у README та назвати спосіб первинної діагностики помилки.

3 Забезпечення та підготовка до заняття

3.1 Матеріальне і програмне забезпечення

Потрібні комп’ютер викладача з проєктором, робоче місце для кожного слухача, доступ до Інтернету для GitHub, Windows, Git for Windows, VS Code, Python 3.11 або новіший та стабільна підтримувана версія PostgreSQL. Для Python і PostgreSQL використовуйте узгоджені для групи версії.

У VS Code потрібні розширення Python від Microsoft, ms-python.python, і PostgreSQL від Microsoft, ms-ossdata.vscode-pgsql. Jupyter потрібен лише для відкриття навчальних блокнотів, якщо вони використовуються. pgAdmin є додатковим клієнтом; основний маршрут заняття проходить через VS Code, резервний — через psql.

Матеріали для слухачів — Практичний_посібник_1_3.html та Посібник_1_3.md у цій самій папці. Посібник містить покрокове встановлення компонентів. Файл practice3.ipynb у навчальному репозиторії задає мінімальний склад практичної роботи.

3.2 Дії викладача напередодні

1. Узгодити з адміністратором встановлення програм та запуск служби PostgreSQL. Перевірити права створення робочих папок, доступ до GitHub, python.org і Marketplace VS Code.

2. Надати слухачам посібник і запропонувати створити облікові записи GitHub заздалегідь. Перевірити доступ до пошти та можливість входу з другого фактора, якщо він налаштований.

3. Пройти весь маршрут на навчальному комп’ютері зі звичайними правами слухача. Підготувати порожній демонстраційний репозиторій для показу та окремий завершений зразок для перевірки.

4. Установити сервер PostgreSQL у Windows, перевірити службу, порт і підключення. Пароль користувача postgres кожний слухач зберігає приватно. Не роздавати один спільний пароль для всіх комп’ютерів.

5. Підготувати локальну копію файлів check.py і schema.sql на випадок недоступності мережі. Під час роботи використовувати лише навчальні дані.

6. Підготувати перелік слухачів із позначками КТ1–КТ4 для оперативного контролю. На спільних комп’ютерах перевірити, чи не залишилися активними чужі GitHub-акаунти.

Організаційна умова: повне встановлення всіх продуктів на всіх комп’ютерах початківців не вкладається надійно у 90 хвилин. До основного заняття інструменти мають бути встановлені або підготовлені адміністратором. На занятті викладач пояснює призначення компонентів і показує ключові параметри встановлення. Якщо комп’ютери не підготовлено, окремо організовується установчий практикум за розділами 2–6 посібника; невиконані дії не зараховуються як виконані.

3.3 Перевірка готовності робочого місця

У PowerShell мають виконуватися наведені команди. Для psql допускається повний шлях до програми, якщо каталог bin ще не додано до Path.

git --version
code --version
python --version
psql --version

Показ версії psql підтверджує наявність клієнта. Роботу сервера викладач перевіряє окремим підключенням:

psql -h localhost -p 5432 -U postgres -d postgres

У psql виконує SELECT current_database(), current_user; і завершує сеанс командою \q. Якщо порт змінено під час встановлення, надалі всюди використовує фактичний порт.

5 Загальні методичні вказівки

Основний прийом — «пояснення → показ однієї завершеної дії → повторення слухачами → перевірка результату». Не демонструвати поспіль кілька екранів, доки слухачі не повторили попередню дію. Після кожного короткого показу прибрати руки від клавіатури й дати час на самостійне виконання.

Перед будь-якою командою називати місце її введення: PowerShell, редактор Python, SQL-редактор чи поле повідомлення Git. Показувати поточну папку термінала та активну базу SQL. Збільшити шрифт редактора й термінала так, щоб останній ряд був читабельним із кінця аудиторії.

Якщо слухач просить допомоги, спочатку з’ясувати: що він хотів виконати, де вводив команду, що отримав фактично. Просити показати текст повідомлення і шлях. Допомагати виконати наступний крок самостійно, а не завершувати всю вправу за слухача.

Для слухачів, які випереджають групу, передбачено додатковий запис у базу, другий перегляд різниці та коротке налагодження. Ці дії не повинні затримувати основний маршрут. Робота в парі допускається для взаємодопомоги, але особисті облікові дані не передаються; результат кожного слухача перевіряється окремо.

Зв’язок з ІАЗ пояснювати через відтворюваність оброблення даних: код задає процедуру, SQL — структуру зберігання, README — порядок запуску, Git — історію змін. У цьому занятті Python і SQL виконуються окремо; підключення Python до PostgreSQL та створення вебзастосунку виходять за межі базової вправи.

6 Вступна частина

Тривалість — 5 хвилин, від 0 до 5 хвилини.

Викладач перевіряє присутність і готовність робочих місць, оголошує тему, два навчальні питання, очікувані результати та порядок контролю. Повідомляє, де відкрити посібник, і нагадує, що паролі не вводять у навчальні файли або спільний чат.

Орієнтовне вступне пояснення: «Сьогодні кожний підготує невеликий проєкт, виконає Python та SQL і збереже зміни у власному репозиторії. Після кожного етапу ми перевірятимемо конкретний результат. Поки не отримали цей результат, до наступного кроку не переходимо».

Швидка діагностика: попросити відкрити VS Code і показати наявність Git та Python. Запитати, хто вже має обліковий запис GitHub, а хто вперше відкриває редактор. Це організаційне опитування, а не оцінювання ще не вивчених понять.

7 Перше навчальне питання

Основи використання системи контролю версій засобів ІАЗ.

Тривалість — 40 хвилин, від 5 до 45 хвилини. Результат — власний репозиторій, його локальна копія, папка 1.3 з README.md та .gitignore, перший власний коміт на GitHub.

7.1 Пояснення призначення контролю версій

5–11 хвилина, 6 хвилин.

Викладач наводить ситуацію: у групі є кілька файлів з назвами «аналіз», «аналіз_новий», «аналіз_остаточний». З’ясувати, хто і що змінив, складно. Git дає історію комітів з автором, описом і різницею; GitHub надає віддалене місце для репозиторію та співпраці.

На екрані послідовно пояснити шість понять: репозиторій — файли та їх історія; робоча папка — поточні файли; stage — вибір змін до коміту; commit — локальний знімок підготовлених змін; push — надсилання комітів на GitHub; clone — створення локальної копії віддаленого репозиторію. Гілку описати як окрему лінію роботи; відпрацювання групового процесу перенести в самостійну роботу.

Питання групі: «Файл збережено Ctrl+S. Чи вже бачить його викладач у GitHub?» Очікувана відповідь: ні, потрібні commit і push. Підкреслити, що локальний commit не потребує Інтернету.

7.2 Перевірка Git та авторства

11–16 хвилина, 5 хвилин.

Викладач показує перевірку git --version та відокремлює ім’я автора коміту від входу до GitHub. На власному комп’ютері можна використати git config --global за посібником. На спільному робочому місці доцільно налаштувати автора локально після клонування, щоб не змінювати налаштування інших проєктів.

Слухач відкриває власний GitHub у браузері. Викладач перевіряє готовність до створення репозиторію, не збираючи паролі. Якщо вхід не працює, слухач отримує допомогу окремо; інші продовжують після короткого пояснення.

7.3 Створення репозиторію та клонування

16–27 хвилина, 11 хвилин.

1. Викладач показує New repository у GitHub. Слухач створює iaz-practicals, обирає приватність відповідно до вимог викладача і вмикає Add README. Початковий README створює початковий коміт і гілку.

2. Слухач копіює HTTPS-адресу зі своєї сторінки Code. У VS Code виконує Ctrl+Shift+P → Git: Clone, вставляє адресу, обирає батьківську папку C:\IAZ_Labs або власну доступну папку.

3. Після клонування слухач натискає Open. Перевіряє, що Explorer показує корінь iaz-practicals. На спільному комп’ютері перевіряє, під чиїм обліковим записом проходить авторизація.

4. У новому терміналі виконує наведені команди. Якщо ім’я та пошту ще не задано, встановлює їх локально для цього репозиторію, замінивши приклади власними даними.

Get-Location
git remote -v
git status
git config user.name "Ваше ім’я"
git config user.email "your-address@example.com"

Контрольна точка КТ1: поточна папка — корінь iaz-practicals; origin веде до власного репозиторію; Git розпізнає робочу папку. Клонування вже створило .git; повторний git init у папці 1.3 не потрібний.

7.4 Папка заняття та підготовка змін

27–36 хвилина, 9 хвилин.

Викладач коротко показує Explorer, створення папки та збереження файла. Слухач створює у корені папку 1.3 і в ній два файли. Для 1.3/README.md використовує початковий текст:

# Тема 1.3. Перше середовище для ІАЗ

## Мета
Підготувати Git, VS Code, Python і PostgreSQL.

## Результати
- Git: репозиторій клоновано.
- Python: ще не перевірено.
- PostgreSQL: ще не перевірено.

У 1.3/.gitignore записує:

.venv/
__pycache__/
.env
*.pyc

Викладач пояснює: .gitignore залишається у репозиторії; його правила приховують від додавання відповідні локальні файли, які ще не відстежуються. Тут .venv буде створено всередині 1.3. Правила з 1.3/.gitignore не поширюються на папки вище 1.3.

Слухач зберігає файли Ctrl+S, відкриває Source Control та переглядає зміни. Викладач запитує, які саме файли мають потрапити в коміт і чому серед них немає паролів.

7.5 Перший коміт і надсилання

36–45 хвилина, 9 хвилин.

У Source Control слухач додає до Stage саме README.md і .gitignore папки 1.3, вводить повідомлення Add 1.3 workspace і натискає Commit, далі … → Push. Авторизацію виконує власним обліковим записом через запропонований браузерний вхід. Якщо команда Git запитує пароль для HTTPS, звичайний пароль GitHub не використовують; порядок входу уточнюють за офіційною документацією або з викладачем.

Еквівалентні команди показати як довідку, не вимагати повторного коміту після виконання через кнопки:

git add 1.3/README.md 1.3/.gitignore
git commit -m "Add 1.3 workspace"
git push
git log -3 --oneline

Контрольна точка КТ2: після оновлення браузера на GitHub видно обидва файли і власний коміт слухача. Початковий автоматичний коміт README не є заміною коміту слухача. Для приватного репозиторію викладач перевіряє екран або попередньо наданий доступ.

Проміжний висновок викладача: слухачі створили віддалений репозиторій, локальну копію та відправили зміни. Після виконання коду вони повторять той самий цикл для результатів практики.

8 Друге навчальне питання

Основи використання інтегрованих середовищ розробника засобів ІАЗ.

Тривалість — 40 хвилин, від 45 до 85 хвилини. Результат — виконаний check.py, створена таблиця PostgreSQL, завершений README та другий власний коміт із файлами на GitHub.

8.1 Пояснення складових середовища

45–50 хвилина, 5 хвилин.

Викладач показує Explorer, редактор, Terminal, Source Control та Extensions. Пояснює, що VS Code з розширеннями об’єднує робочі інструменти, але запуск забезпечують окремо встановлені програми.

Ключове пояснення: «Розширення Python працює з інтерпретатором Python. Розширення PostgreSQL підключається до сервера PostgreSQL. Сам сервер установлюється у Windows і працює як служба. Закриття редактора не означає зупинку сервера».

На слайді або вікні демонстрації показати ключові поля установника PostgreSQL: PostgreSQL Server, Command Line Tools, каталог програми, окремий каталог даних, пароль postgres і порт 5432. Stack Builder для цієї вправи не потрібний. Якщо слухачі встановлюють самостійно, направити до розділу 6 посібника, а не пропускати встановлення сервера.

Запитати: «Якщо psql --version показує номер, чи доведено, що сервер приймає з’єднання?» Очікувано: ні, потрібне підключення.

Якщо для створення середовища доступна лише команда py, перший рядок починається з py. У VS Code слухач обирає Python: Select Interpreter → 1.3\.venv\Scripts\python.exe. Прямий запуск цього python.exe не потребує активації Activate.ps1, тому не потрібно змінювати політику PowerShell.

Очікуваний результат:

Контрольна точка КТ3: кожний слухач показує вивід на власному робочому місці й пояснює, звідки взялося число 25. Наявність файла check.py без його запуску не підтверджує виконання вправи.

8.3 Підключення PostgreSQL та виконання SQL

62–78 хвилина, 16 хвилин.

Викладач проводить групу через три окремі перевірки: працює служба → є з’єднання → запит виконався в потрібній базі. Паролі на проєкторі не демонструє.

1. У панелі PostgreSQL слухач додає підключення: Server name — localhost; Port — фактичний порт, типовий 5432; Authentication Type — Password; User name — postgres; Database name — postgres; Password — власний пароль, заданий під час встановлення. Натискає Save & Connect. На спільному робочому місці пароль не зберігає.

2. Відкриває New Query і виконує окрему команду CREATE DATABASE iaz_lab; лише якщо базу ще не створено. Вона потребує відповідних прав і не виконується всередині BEGIN. При повідомленні про наявну базу слухач її не видаляє.

3. Перемикає базу підключення на iaz_lab або створює друге підключення з цим ім’ям. Виконує SELECT current_database(); і отримує iaz_lab.

4. Створює 1.3/schema.sql, зберігає і виконує його текст у підключеному SQL-редакторі для iaz_lab.

CREATE TABLE IF NOT EXISTS test_data (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL
);

Для запуску у PostgreSQL-редакторі використовується кнопка виконання або Ctrl+Shift+E. Якщо збережений файл не має підключення, слухач копіює його текст у New Query для iaz_lab. SQL не вводять як окрему команду PowerShell.

Перевірка після створення:

SELECT current_database();
SELECT id, name FROM public.test_data;

Очікувано: iaz_lab та таблиця зі стовпцями id, name. У щойно створеній таблиці 0 рядків — нормальний результат. Якщо таблиця існувала, наявні рядки не видаляють заради повторення вправи. IF NOT EXISTS не перевіряє відповідність структури вже наявної таблиці, тому для демонстрації викладач використовує заздалегідь перевірену навчальну базу.

Додаткове завдання для тих, хто завершив основне: у New Query виконати блок нижче. При повторному послідовному запуску він не додає ще одного такого самого навчального запису.

INSERT INTO public.test_data (name)
SELECT 'Навчальний запис'
WHERE NOT EXISTS (
    SELECT 1 FROM public.test_data
    WHERE name = 'Навчальний запис'
);
SELECT id, name FROM public.test_data ORDER BY id;

Контрольна точка КТ4: слухач показує ім’я бази iaz_lab і успішний SELECT із test_data. Якщо виконано додатковий блок, видно Навчальний запис. Номер id не є критерієм успіху. У навчальному середовищі використовується локальний postgres; для реального застосунку потрібен окремий обліковий запис із необхідними правами.

Викладач окремо уточнює: коміт schema.sql зберігає інструкцію створення таблиці. Він не переносить сервер, саму базу чи її записи на GitHub.

9 Контроль засвоєння та оцінювання

9.1 Докази виконання

Викладач перевіряє роботу безпосередньо на екрані слухача або за наданими файлами та результатами. Скриншот доповнює перевірку, але не замінює пояснення. На приватний репозиторій слухач надає доступ узгодженим способом.

Рекомендована шкала нижче є інструментом поточного контролю; її застосовують після узгодження з чинною системою оцінювання дисципліни. Вона не замінює затверджені вимоги.

СкладоваМаксимумУмова повного бала

Для складової на 2 бали часткове виконання з розумінням наступного кроку дає 1 бал; непідтверджений результат — 0. Для Git: 1 бал за власний локальний коміт, 1 за його появу на GitHub, 1 за правильне пояснення різниці між збереженням, commit і push. Самостійність фіксується коментарем викладача; звернення початківця по допомогу не є автоматичною підставою для зниження оцінки.

Якщо результат не отримано через несправність класу чи мережі, викладач записує причину й організовує повторну перевірку. Локальний коміт без push не позначають як успішне надсилання; недоступний сервер не підміняють скриншотом зразка.

9.2 Запитання та орієнтовні відповіді

1. Чим Git відрізняється від GitHub? Git керує історією локально; GitHub розміщує віддалені репозиторії та засоби співпраці.

2. Чим відрізняються Ctrl+S, commit і push? Запис файла на диск; локальний знімок підготовлених змін; надсилання комітів до віддаленого репозиторію.

3. Навіщо потрібен .gitignore? Щоб не пропонувати до додавання відповідні локальні файли, які ще не відстежуються, зокрема .venv та кеш.

4. Чи встановлює розширення PostgreSQL сервер? Ні; воно підключається до окремо встановленого та запущеного сервера.

5. Чому SELECT повернув 0 рядків? Таблиця існує, але в ній ще немає даних; це не помилка виконання.

6. Як з’ясувати активну базу? Виконати SELECT current_database(); у підключеному SQL-редакторі.

7. Чи містить GitHub дані бази після push schema.sql? У цьому завданні збережено лише SQL-файл; дані залишаються на локальному сервері.

8. Чому Python у терміналі може відрізнятися від обраного у VS Code? Термінал використовує власний PATH або активоване середовище. Прямий шлях до .venv\Scripts\python.exe однозначно задає інтерпретатор.

10 Типові помилки та дії викладача

Git не знайдено або відкрито неправильну папку

Уточнити, чи завершено встановлення Git. Перезапустити редактор і термінал після зміни PATH. Якщо git status показує not a git repository, перевірити Get-Location і відкрити клоновану папку через File → Open Folder. Не створювати ще один .git навмання.

Не виконано вхід або push відхилено

Перевірити власника origin та активний GitHub-акаунт. Помилку авторства коміту виправляти налаштуванням user.name і user.email, а помилку доступу — входом або правами. При non-fast-forward зберегти локальні зміни й окремо узгодити віддалені; Force Push початківцям для цього заняття не застосовувати.

У Source Control з’явилася .venv

Перевірити розташування середовища саме у 1.3/.venv, назву 1.3/.gitignore та його збереження. Перевірка — git check-ignore -v 1.3/.venv/pyvenv.cfg. Якщо файли вже відстежуються, потрібне контрольоване вилучення з індексу; не видаляти робоче середовище замість виправлення Git.

Python не знаходить файл або показує помилку кодування

Перевірити поточну папку, назву check.py без .txt, збереження файла та UTF-8 у редакторі. Використати прямий запуск із -X utf8. Якщо Activate.ps1 заборонено, запускати .venv\Scripts\python.exe без активації й не вимикати захист PowerShell.

PostgreSQL відмовляє у з’єднанні

Перевірити службу у services.msc, адресу localhost і порт. Connection refused вказує на недоступність сервера за цими параметрами; password authentication failed — на проблему облікових даних. Не лікувати обидва повідомлення однаково. Для локальної вправи не відкривати порт у зовнішню мережу та не вимикати брандмауер.

Таблицю не знайдено або база вже існує

Перевірити SELECT current_database();. Переконатися, що schema.sql дійсно виконано у iaz_lab, а не лише збережено на диску. Існуючу навчальну базу використовувати повторно; не видаляти її лише для усунення повідомлення already exists.

Окремий комп’ютер або мережа не працює

Не зупиняти всю групу на тривале налаштування одного робочого місця. Зафіксувати причину, пересадити слухача на підготовлене місце або організувати парне виконання з подальшою особистою перевіркою. Без Інтернету можливі локальні файли, commit, Python і SQL; push перевіряється після відновлення мережі.

Якщо розширення PostgreSQL недоступне, використати psql із кореня репозиторію. База iaz_lab має бути створена заздалегідь:

psql -h localhost -p 5432 -U postgres -d iaz_lab -v ON_ERROR_STOP=1 -f .\1.3\schema.sql
psql -h localhost -p 5432 -U postgres -d iaz_lab -c "SELECT id, name FROM public.test_data;"

12 Завдання на самостійну роботу

Налаштування середовища розробника для виконання індивідуальних та групових проектів.

12.1 Індивідуальна частина

1. Повторно відкрити власний репозиторій у VS Code, перевірити інтерпретатор .venv та виконати check.py без копіювання готового виводу.

2. Відновити підключення до iaz_lab, перевірити test_data і за бажанням виконати додатковий навчальний INSERT із посібника.

3. Створити 1.3/environment.md. Записати версії Windows, Git, VS Code, Python і PostgreSQL, відносний шлях до .venv, ідентифікатори розширень, команди запуску та одну власну помилку зі способом перевірки. Паролі, токени та особисті шляхи профілю не зазначати.

4. Додати у README порядок повторного запуску. Перевірити .gitignore, зробити коміт із зрозумілим повідомленням і виконати push.

Результат індивідуальної частини — посилання на коміт, environment.md та коротка демонстрація запуску. Викладач перевіряє, чи можна за інструкцією слухача повторити виконання на його робочому місці.

12.2 Групова частина

Працювати групами по 2–3 особи, зберігаючи індивідуальні облікові записи. Викладач визначає склад груп і репозиторій; строк подання повідомляє відповідно до розкладу.

1. Один учасник створює окремий навчальний груповий репозиторій, наприклад iaz-team-lab, і надає іншим учасникам доступ. Усі приймають запрошення та клонують його у власні локальні папки.

2. У корені репозиторію група додає .gitignore для .venv/, __pycache__/, .env і *.pyc, а в README — мету, узгоджені версії та порядок запуску. Кожний створює власне локальне середовище; .venv між комп’ютерами не копіюють.

3. Кожний учасник створює окрему гілку, наприклад docs/імя-латиницею, і додає власний файл docs/імя-латиницею.md з перевіреними кроками налаштування одного компонента. У назвах замінює умовний текст на власний короткий ідентифікатор латиницею. Для першої вправи різні файли зменшують кількість конфліктів.

4. Учасник робить commit, публікує свою гілку, відкриває pull request у GitHub і просить іншого учасника перевірити інструкцію. Рецензент перевіряє зміст та залишає конкретне зауваження або підтвердження; автор виправляє за потреби.

5. Після перевірки відповідальний учасник зливає зміни. Усі переходять на основну гілку і отримують оновлення через pull, переконавшись, що локальні зміни збережено. Назву основної гілки перевіряють у репозиторії; вона не завжди main.

Результат групової частини — спільний README, внесок кожного учасника в історії, щонайменше один pull request від кожного та підтвердження взаємної перевірки. Група коротко пояснює, хто що змінив і як інший учасник отримав ці зміни. Послідовність відповідає базовому GitHub flow.

Оцінювання самостійної роботи: індивідуальний запуск і документація, особистий внесок у групу та здатність повторити дії. Загальний бал і строки встановлюються за системою дисципліни; готовий груповий файл без підтвердження особистого внеску не є достатнім результатом.
